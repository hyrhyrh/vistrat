# 任务健康监控和自动恢复机制

## 问题背景

### 原有问题

系统存在一个严重的漏洞：

1. **系统重启时** - ✅ 可以通过 `auto_recover_tasks` 恢复所有启用的任务
2. **运行时故障** - ❌ 如果视频流异常或任务崩溃，任务会永久停止，无法自动恢复

具体场景：
- 系统运行了一天后，某个视频流因网络抖动短暂掉线
- 视频流分析任务因此停止
- 即使视频流恢复正常，任务也不会自动重启
- **结果：分析任务永久停止，直到手动重启或系统重启**

## 解决方案

### 核心架构

创建了 `TaskHealthMonitor` 服务，提供完整的健康监控和自动恢复机制：

```
┌─────────────────────────────────────────────────────────────┐
│                  TaskHealthMonitor                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌──────────────────┐        ┌──────────────────┐          │
│  │  任务健康检查     │        │  视频流监控       │          │
│  │  (每5分钟)       │        │  (每10分钟)      │          │
│  └──────────────────┘        └──────────────────┘          │
│           │                           │                     │
│           ▼                           ▼                     │
│  ┌──────────────────┐        ┌──────────────────┐          │
│  │  检查应运行任务   │        │  RTSP健康检查    │          │
│  │  是否真的在运行   │        │  更新流状态      │          │
│  └──────────────────┘        └──────────────────┘          │
│           │                           │                     │
│           ▼                           ▼                     │
│  ┌──────────────────┐        ┌──────────────────┐          │
│  │  智能重试策略     │        │  流恢复时重启     │          │
│  │  (指数退避)      │        │  相关任务        │          │
│  └──────────────────┘        └──────────────────┘          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 主要功能

#### 1. 任务健康检查

**检查流程：**
1. 查询数据库中所有 `status='enabled' AND is_active=true` 的任务
2. 检查任务是否在配置的运行时间范围内
3. 验证任务是否真正在 `stream_analysis_service.running_tasks` 中运行
4. 如果应该运行但没运行，尝试自动恢复

**检查频率：** 默认每5分钟（可配置）

#### 2. 视频流健康监控

**监控流程：**
1. 查询所有RTSP视频流
2. 使用 `rtsp_health_checker` 检查流的可访问性
3. 更新数据库中的 `video_streams.status` 字段
4. 检测状态变化（离线→在线）
5. 当流恢复时，自动重启相关的分析任务

**检查频率：** 默认每10分钟（可配置）

#### 3. 智能重试策略（指数退避）

为避免频繁重试浪费资源，采用指数退避策略：

| 连续失败次数 | 重试间隔 |
|-------------|---------|
| 0-1次       | 5分钟   |
| 2-3次       | 10分钟  |
| 4-5次       | 20分钟  |
| 6次以上     | 1小时   |

**关键逻辑：**
```python
def _calculate_retry_delay(consecutive_failures: int) -> int:
    if consecutive_failures <= 1:
        return 5 * 60  # 5分钟
    elif consecutive_failures <= 3:
        return 10 * 60  # 10分钟
    elif consecutive_failures <= 5:
        return 20 * 60  # 20分钟
    else:
        return 60 * 60  # 1小时
```

#### 4. 详细的记录追踪

**任务恢复记录（TaskRecoveryRecord）：**
- 最后检查时间
- 失败次数
- 恢复尝试次数
- 连续失败次数
- 最后错误信息

**视频流健康记录（StreamHealthRecord）：**
- 当前状态（在线/离线）
- 最后检查时间
- 最后在线/离线时间
- 检查次数
- 连续失败次数
- 最后错误信息

## 配置参数

在 `backend/config/settings.py` 中添加了 `HealthMonitorConfig` 类：

```python
class HealthMonitorConfig:
    # 任务健康检查间隔（秒），默认5分钟
    TASK_HEALTH_CHECK_INTERVAL = int(os.getenv("TASK_HEALTH_CHECK_INTERVAL", "300"))

    # 视频流健康检查间隔（秒），默认10分钟
    STREAM_HEALTH_CHECK_INTERVAL = int(os.getenv("STREAM_HEALTH_CHECK_INTERVAL", "600"))

    # 基础重试延迟（秒），默认5分钟
    RETRY_DELAY_BASE = int(os.getenv("RETRY_DELAY_BASE", "300"))

    # 最大重试延迟（秒），默认1小时
    MAX_RETRY_DELAY = int(os.getenv("MAX_RETRY_DELAY", "3600"))

    # 最大连续失败次数，超过后延长重试间隔
    MAX_CONSECUTIVE_FAILURES = int(os.getenv("MAX_CONSECUTIVE_FAILURES", "5"))

    # 是否启用任务健康监控
    ENABLE_HEALTH_MONITOR = os.getenv("ENABLE_HEALTH_MONITOR", "true").lower() == "true"
```

### 环境变量配置

可以通过 `.env` 文件自定义配置：

```bash
# 任务健康监控配置
ENABLE_HEALTH_MONITOR=true           # 启用健康监控
TASK_HEALTH_CHECK_INTERVAL=300       # 任务检查间隔（秒）
STREAM_HEALTH_CHECK_INTERVAL=600     # 视频流检查间隔（秒）
RETRY_DELAY_BASE=300                 # 基础重试延迟（秒）
MAX_RETRY_DELAY=3600                 # 最大重试延迟（秒）
MAX_CONSECUTIVE_FAILURES=5           # 最大连续失败次数
```

## 系统集成

### 启动流程

在 `main.py` 的 `lifespan` 函数中：

```python
# 启动任务健康监控服务
from config.settings import HealthMonitorConfig
if HealthMonitorConfig.ENABLE_HEALTH_MONITOR:
    from services.task_health_monitor import task_health_monitor
    task_health_monitor.check_interval = HealthMonitorConfig.TASK_HEALTH_CHECK_INTERVAL
    task_health_monitor.stream_check_interval = HealthMonitorConfig.STREAM_HEALTH_CHECK_INTERVAL
    await task_health_monitor.start()
    logger_ctx.info("✅ 任务健康监控服务已启动")
```

### 关闭流程

```python
# 停止任务健康监控服务
from services.task_health_monitor import task_health_monitor
await task_health_monitor.stop()
```

## 优势

1. **自动化** - 无需人工干预，自动检测和恢复
2. **智能重试** - 避免频繁重试浪费资源
3. **全面监控** - 同时监控任务状态和视频流健康
4. **详细记录** - 完整的日志和统计信息
5. **可配置** - 所有参数都可通过环境变量调整
6. **API可视化** - 提供完整的API端点查看监控状态

## 性能影响

- **内存占用** - 极低（每个任务/流记录约1KB）
- **CPU占用** - 极低（检查操作非常轻量）
- **网络影响** - 仅在检查视频流时产生少量网络请求
- **数据库影响** - 最小（仅在状态变化时更新数据库）

## 故障恢复能力

### 监控服务本身崩溃
- 系统重启时会自动重新启动监控服务
- 监控服务的任务记录会重新初始化

### 数据库连接失败
- 监控服务会记录错误并继续运行
- 下次检查时会重新尝试连接

### 所有任务都失败
- 监控服务会持续尝试恢复
- 根据智能重试策略逐步延长重试间隔

## 未来增强

可能的改进方向：

1. **持久化恢复记录** - 将恢复记录保存到数据库
2. **告警通知** - 当任务持续失败时发送告警
3. **自适应间隔** - 根据系统负载动态调整检查间隔
4. **批量恢复** - 优化多任务同时恢复的性能
5. **Web界面** - 前端可视化监控仪表板

## 总结

这个任务健康监控和自动恢复机制彻底解决了原有的运行时任务停止问题：

✅ **系统重启时** - 通过 `auto_recover_tasks` 恢复任务
✅ **运行时故障** - 通过 `TaskHealthMonitor` 自动检测和恢复
✅ **视频流异常** - 监控流状态，恢复时自动重启任务
✅ **智能重试** - 避免频繁重试浪费资源
✅ **完整监控** - 详细的日志和统计信息

现在，无论是系统重启、视频流异常还是任务崩溃，系统都能自动检测并恢复，确保视频分析任务的持续运行！
